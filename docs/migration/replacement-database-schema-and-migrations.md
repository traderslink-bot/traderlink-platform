7. No legacy/replacement dual writes are permitted. The legacy database remains read-only migration input until a later authorized Journal migration.
8. The replacement database layer uses TraderLink Platform and module names only. It has no V3 naming, V3 analytics import, V3 authority/replay/proof dependency, or V3 database accessor.

Broker/source account fingerprinting uses two server-only settings:

- `TRADERLINK_PLATFORM_ACCOUNT_IDENTITY_HMAC_KEYS_JSON`: a JSON object whose property names are immutable HMAC key-version identifiers and whose values are base64-encoded secrets; and
- `TRADERLINK_PLATFORM_ACCOUNT_IDENTITY_ACTIVE_KEY_VERSION`: the key version used for newly written fingerprints.

Each decoded secret must be at least 32 cryptographically random bytes generated by a CSPRNG. These settings are not required to initialize an empty database, but account-source identity creation or matching fails safely when the active key, a referenced retained key, or a required adapter canonicalizer is unavailable. Secrets are never stored in SQLite, logged, sent to the browser, placed in source control, or copied from the legacy `.env.local`.

A key-version label is immutable: its secret value may never be replaced in place. Rotation always adds a new version and retains the old labeled secret for matching and recovery until the explicit retirement gate below succeeds.

## 2. Module-owned migration structure

The migration runner belongs to Platform because it owns the physical database lifecycle. Each migration remains logically owned by one module and is located under that module's server-only directory.

Approved initial module namespaces:

- `platform`
- `journal`

A namespace must match `^[a-z][a-z0-9_]*$`. A future module adds its own namespace and migrations through the central manifest; it may not edit another module's migration or query another module's private tables.

The runner statically imports migration descriptors. It does not scan arbitrary files at runtime. Every descriptor has exactly:

```ts
type PlatformMigration = Readonly<{
  moduleNamespace: "platform" | "journal";
  migrationId: string;
  executionOrder: number;
  statements: readonly string[];
}>;
```

Future namespace additions extend the type deliberately. Migration IDs match `^[0-9]{4}_[a-z0-9_]+$` and are globally unique across modules.

| 1 | `platform` | `0001_platform_identity` | `src/modules/platform/server/database/migrations/0001_platform_identity.ts` | `platform_users`, `platform_workspaces`, `platform_workspace_memberships`, and their indexes |

Filename-to-ID matching is a focused static repository rule, not runtime descriptor behavior. The proposed `src/scripts/verify-traderlink-platform-migration-files.ts` reads the statically configured migration paths and exported literal metadata, then requires each filename stem to equal its `migrationId`. The runtime descriptor has no source-filename field and never claims to infer where its module was loaded from.

## 3. Exact migration registry

The runner owns this table and creates it only when the target has no user-defined tables:

```sql
CREATE TABLE platform_schema_migrations (
  migration_id TEXT PRIMARY KEY
    CHECK (
      length(migration_id) >= 6
      AND migration_id GLOB '[0-9][0-9][0-9][0-9]_*'
      AND migration_id NOT GLOB '*[^a-z0-9_]*'
    ),
  module_namespace TEXT NOT NULL
    CHECK (
      module_namespace GLOB '[a-z]*'
      AND module_namespace NOT GLOB '*[^a-z0-9_]*'
    ),
  execution_order INTEGER NOT NULL CHECK (execution_order > 0),
  checksum_sha256 TEXT NOT NULL
    CHECK (
      length(checksum_sha256) = 64
      AND checksum_sha256 = lower(checksum_sha256)
      AND checksum_sha256 NOT GLOB '*[^0-9a-f]*'
    ),
  post_schema_sha256 TEXT NOT NULL
    CHECK (
      length(post_schema_sha256) = 64
      AND post_schema_sha256 = lower(post_schema_sha256)
      AND post_schema_sha256 NOT GLOB '*[^0-9a-f]*'
    ),
  applied_at_utc TEXT NOT NULL
    CHECK (
      length(applied_at_utc) = 24
      AND applied_at_utc GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]T[0-9][0-9]:[0-9][0-9]:[0-9][0-9].[0-9][0-9][0-9]Z'
    ),
  sqlite_version TEXT NOT NULL CHECK (length(sqlite_version) > 0),
  UNIQUE (execution_order)
) STRICT, WITHOUT ROWID;
```

`applied_at_utc` is generated by the server as an RFC 3339 UTC instant with millisecond precision immediately before the registry insert. `sqlite_version` records `sqlite_version()` from the same connection.

### Migration checksum rules

For each descriptor, the runner:

1. validates the namespace, globally unique ID, positive globally unique execution order, and non-empty statement list;
2. preserves all statement whitespace except line endings;
3. normalizes CRLF and CR to LF in each statement;
4. joins statements with the exact separator `\n-- traderlink-statement-boundary --\n`;
5. removes trailing LF characters from the joined value and then appends exactly one LF; and
6. stores the lowercase SHA-256 hexadecimal digest of those UTF-8 bytes.

Comments and formatting are checksum-bearing content. An applied migration is immutable; a correction is a new migration with a new global execution order.

### Deterministic post-migration schema digest

`post_schema_sha256` records the exact schema produced by each applied migration. It is separate from `checksum_sha256`: the migration checksum proves the declared migration statements have not changed, while the post-schema digest detects a table, explicit index, view, or trigger that changed after the migration was recorded.

The runner and verifier use this one algorithm:

1. Read the user-defined schema rows with the following query. The `sqlite_` exclusion omits SQLite-internal objects, including automatically generated indexes. The registry table itself and every application table, explicit index, view, and trigger remain included.

   ```sql
   SELECT type, name, tbl_name, sql
   FROM sqlite_schema
   WHERE type IN ('table', 'index', 'view', 'trigger')
     AND substr(name, 1, 7) <> 'sqlite_'
   ORDER BY
     type COLLATE BINARY,
     name COLLATE BINARY,
     tbl_name COLLATE BINARY;
   ```

2. Require `type`, `name`, `tbl_name`, and `sql` to be non-null strings for every selected row. Normalize only the `sql` value's line endings by replacing CRLF and bare CR with LF; do not trim or otherwise reformat it.
3. Represent each ordered row as the four-element array `[type, name, tbl_name, normalizedSql]`.
4. Serialize the ordered array of row arrays with JavaScript's deterministic `JSON.stringify` and no replacer or spacing, append exactly one LF, encode those bytes as UTF-8, and calculate SHA-256.
5. Encode the result as required lowercase 64-character hexadecimal and compare it with or store it in `post_schema_sha256` as required by the current mode.

The digest covers schema definitions, not registry row data, so calculating it immediately before the registry insert is not circular. `PRAGMA schema_version` is SQLite's internal schema-cache cookie; it is neither the migration authority nor input to this schema digest.

### Duplicate, changed, and unknown migration behavior

The manifest is validated before any database mutation.

- A duplicate `executionOrder` fails with `TRADERLINK_MIGRATION_ORDER_CONFLICT`.
- A duplicate `migrationId` fails with `TRADERLINK_MIGRATION_ID_CONFLICT`.
- A filename/ID mismatch fails the static repository verification with `TRADERLINK_MIGRATION_FILE_ID_MISMATCH`; it is not a runtime descriptor check.
- An applied row whose order and checksum match the descriptor is skipped idempotently.
- An applied ID whose checksum or execution order differs fails with `TRADERLINK_MIGRATION_CHECKSUM_MISMATCH`. The runner never updates the historical row.
- A required schema-digest comparison that differs from the recorded `post_schema_sha256` fails with `TRADERLINK_PLATFORM_SCHEMA_MISMATCH`. The runner, initializer, ordinary runtime, and verifier never repair, replace, or adopt the changed schema or digest automatically.
- A registry row with no matching descriptor fails with `TRADERLINK_MIGRATION_UNKNOWN_APPLIED`.
- A lower-order missing migration beneath an already applied higher order fails with `TRADERLINK_MIGRATION_ORDER_CONFLICT`; migrations are never backfilled out of sequence.
- A database with application tables but no registry fails with `TRADERLINK_PLATFORM_UNMANAGED_SCHEMA`; the initializer does not adopt or overwrite it.

### Transaction and failure behavior

The migration runner is invoked only by the explicit initializer. It opens one writable connection, configures its connection settings, validates the complete manifest and registry state, and then applies pending migrations in ascending global order. On an absent or empty target with no user-defined tables, the first migration transaction creates the registry before executing migration 1. If migration 1 fails, that same rollback removes the new registry and all migration-1 objects; an empty SQLite file and empty sidecars may remain and are eligible only for an initializer retry. On an existing managed target, the registry must already be present.

Each migration runs in its own `BEGIN IMMEDIATE` transaction. The exact transaction sequence is: execute the migration's declared statements; execute `PRAGMA foreign_key_check` and require no rows; calculate the resulting deterministic schema digest; insert the registry row with the migration-content `checksum_sha256`, resulting `post_schema_sha256`, applied timestamp, and SQLite version; then commit. The digest is therefore calculated after the statements and foreign-key check succeed but before the registry row is inserted. On any statement, foreign-key check, digest calculation, registry insert, or commit failure, SQLite rolls back that migration completely, the runner closes the connection, reports `TRADERLINK_MIGRATION_FAILED` with the non-private migration ID, and stops. Earlier successfully committed migrations and registry rows remain valid. Before a later explicit initializer resumes, it validates that those rows are an exact leading prefix of the manifest and compares the actual schema digest with the latest applied row's `post_schema_sha256`; ordinary startup rejects the partial state with `TRADERLINK_PLATFORM_MIGRATIONS_PENDING`. No later migration runs after a failure.

After all pending migrations, the runner compares the actual schema digest with the final migration row and requires `PRAGMA quick_check` to return `ok`. A schema mismatch fails with `TRADERLINK_PLATFORM_SCHEMA_MISMATCH`; a failed final quick check reports `TRADERLINK_PLATFORM_INTEGRITY_FAILED`. Either failure closes the database and never rewrites migration history or continues application startup. Migration-content checksums, deterministic schema-digest comparison, `PRAGMA foreign_key_check`, `PRAGMA quick_check`, and unknown-table detection remain separate safeguards with separate evidence.

## 4. Shared storage primitives

All initial tables are SQLite `STRICT` tables. Services validate more strongly than SQLite's portable built-in checks.

### Identifiers

- Domain identifiers are lowercase canonical RFC 4122 UUID text, generated on the server. The selected initial generator is UUID v4; IDs never encode owner data.
- Every UUID column requires exactly four hyphens in canonical positions, version nibble `4`, and RFC variant nibble `8`, `9`, `a`, or `b`. The service performs the same strict UUID-v4 validation before every write.
- Migration IDs are the only non-UUID domain-style identifiers and follow the migration rule above.

The exact reusable SQL check expanded inline for a UUID column named `value` is:

```sql
length(value) = 36
AND value = lower(value)
AND length(replace(value, '-', '')) = 32
AND replace(value, '-', '') NOT GLOB '*[^0-9a-f]*'
AND substr(value, 9, 1) = '-'
AND substr(value, 14, 1) = '-'
AND substr(value, 19, 1) = '-'
AND substr(value, 24, 1) = '-'
AND substr(value, 15, 1) = '4'
AND substr(value, 20, 1) GLOB '[89ab]'
```

### Time and trading dates

- Persisted system timestamps are 24-character RFC 3339 UTC text with numeric date/time components, millisecond precision, and a terminal `Z`, for example `2026-08-01T12:34:56.789Z`. Every SQL timestamp check uses the exact numeric GLOB pattern shown in the registry. Service validation parses the instant, rejects impossible calendar/time values, and requires `toISOString()` to equal the submitted text exactly.
- Broker/source timestamps retain the original text plus the adapter/version and source timezone evidence in future source/provenance tables.
- Every Journal account has an explicit IANA `trading_timezone`. Trading dates use `YYYY-MM-DD` interpreted in that timezone.
- Submission/upload time never substitutes for execution time or trading date.

### Exact numeric and currency rules

- Quantity, price, fee, commission, notional, gross P/L, and net P/L source-of-truth values are canonical base-10 strings stored in `TEXT`, never SQLite `REAL` and never JavaScript `number`.
- Canonical decimals contain an optional leading minus, integer digits, and optional fractional digits; they contain no `+`, exponent, grouping separator, whitespace, leading zeroes, trailing fractional zeroes, or negative zero. Zero is exactly `0`.
- Source formatting is retained separately in source-row evidence. Canonicalization never changes the represented value.
- Integer minor units are allowed only in an explicitly named `*_minor` field accompanied by currency and a declared currency exponent. Quantity and price are never minor units.
- Every monetary fact has an explicit uppercase ISO 4217 currency. Values in different currencies are never combined without a separately persisted conversion fact and policy.
- Arithmetic uses `decimal.js` or integer minor-unit operations at the service boundary. JavaScript floating point is never the financial source of truth.

### Isolation

Every account-scoped Journal fact carries and queries by both `workspace_id` and `account_id`. Instrument- and money-bearing facts also carry stable `instrument_id` and explicit `currency`. Workspace-owned definitions such as tags and rules carry `workspace_id` without a fabricated account ID; their account, trading-day, execution, or round-trip association rows carry the applicable narrower identity. Repository methods require server-derived scope and include every applicable isolation key in lookup, uniqueness, rebuild, and aggregation predicates. One workspace, account, instrument, or currency chain cannot be silently joined to another.

Modules may reference only explicitly published identity keys across schema boundaries. They consume another module's facts through that module's server service and published contract; they do not import a foreign repository or issue silent cross-module table queries.

A workspace and its first active owner membership are created in one service transaction. The service prevents archiving a workspace, suspending its owner, or changing/removing its owner membership unless a valid owner transfer occurs in the same transaction. Authentication provider and subject are server-only identity values. `auth_provider` is selected from a server-controlled allowlist and stored as its stable lowercase identifier; it is never derived from arbitrary client text. `auth_subject` is retained exactly, including provider-defined case and whitespace semantics, and is never normalized beyond that provider's contract. Neither value is accepted from a client as authorization or exposed as a user display value.

Account rules:

1. `account_id` is the permanent internal identity used by executions, decisions, round trips, notes, and analytics. A broker rename or corrected source identity does not change it.
2. A manual-only Journal account may exist with no source-identity row. Each `journal_account_source_identities` row is one versioned fingerprint record; multiple current/retained rows may resolve to the same stable `account_id`. Broker ingestion creates or matches these rows only through the Journal account service.
3. `fingerprint_scheme_version` is exactly `hmac-sha256-v1` for the initial scheme. `source_account_canonicalization_version` is the immutable adapter-owned canonicalizer identifier, such as `ibkr-source-account-v1`; adapters must retain every version still referenced by a non-superseded row. `hmac_key_version` identifies the secret-map entry used for that fingerprint without exposing the secret.
4. For `hmac-sha256-v1`, the input is the UTF-8 string `traderlink-account-fingerprint-v1\u001f<source-system>\u001f<canonicalization-version>\u001f<hmac-key-version>\u001f<canonical-source-account-id>`. The service computes HMAC-SHA-256 with the referenced key and stores lowercase hexadecimal.
5. The raw broker account identifier is not stored in these ownership tables, logged, used in a URL, returned to the client, or embedded in fixtures/documentation. It remains only in later authorized private source evidence under its retention rules.
6. `privacy_safe_display` is an explicit neutral label such as `[redacted-account]` or a trader-chosen name. It is never automatically populated with the raw broker identifier. A broker adapter may propose a masked value only after a separate privacy review.
7. The declared foreign keys to Platform workspace/user IDs are published identity-boundary references. Journal repositories never query Platform memberships directly.

### Exact fingerprint matching and rotation

Before matching, the service inventories all non-superseded canonicalization and HMAC key versions referenced for the workspace/source system and fails closed if any required implementation or secret is unavailable. For an incoming broker account, the adapter then produces canonical values for its current and every retained supported canonicalization version. The service computes the Cartesian set of fingerprints across those canonicalization versions and the active plus retained HMAC key versions, then queries by the full tuple `(workspace_id, source_system, fingerprint_scheme_version, source_account_canonicalization_version, hmac_key_version, source_account_fingerprint)`.

- If every match resolves to the same `account_id`, that internal account is reused. Missing current canonicalization/key-version rows are inserted for that account in the same transaction and older rows become `retained_previous`.
- If matches resolve to more than one internal account, the service fails with `TRADERLINK_ACCOUNT_IDENTITY_CONFLICT`; it never merges or chooses automatically.
- If no fingerprint matches, automatic broker-account creation is always prohibited. An active owner/admin `WorkspaceAccessScope` must explicitly confirm, from private source evidence, either a genuinely new internal account or a link to an existing account. This makes lost/changed secrets and canonicalizers fail visibly rather than silently duplicating an account.
- If a required prior canonicalizer or referenced HMAC key is unavailable, matching fails with `TRADERLINK_ACCOUNT_IDENTITY_RECOVERY_REQUIRED`. The service never treats that failure as a new account.
- Account creation, source-identity linking, rotation, supersession, and privacy-safe display changes require an active owner/admin scope in the same workspace and one database transaction.

Key rotation is additive: provision a new strong key/version, retain previous keys, set the new active version, and write a new `active_current` fingerprint only after an old/current fingerprint has resolved the stable `account_id`. A prior row and key are not retired until every affected identity has a current-version row, the rotation report has no conflicts/unmatched records, and database-plus-secret recovery has been verified. Canonicalization-version changes follow the same additive matching rule.

The applicable HMAC secrets are part of recovery authority even though they are not database content. They must be backed up separately in an owner-controlled secret manager or encrypted recovery package, with key-version labels and restore instructions. They must never be stored beside the SQLite backup. A restored database may open without them, but any account matching/import operation referencing unavailable versions must fail closed until the exact secrets are recovered.

### Server-derived `WorkspaceAccessScope`

`requireWorkspaceAccessScope()` is assembled on the server in this order:

1. authenticate the request and map `(auth_provider, auth_subject)` to one active `platform_users` row;
2. resolve only active `platform_workspace_memberships` for that user;
3. accept a requested workspace only as a selector and require it to be in those memberships;
4. for an `owner` or `admin` membership, call the Journal account service to list active account IDs in that workspace;
5. for an initial `member` membership, return no account IDs until a later, explicitly designed Platform account-grant migration exists; and
6. accept an active-account selector only when it is present in the derived allowed-account set.

The resulting server-only contract is:

```ts
type WorkspaceAccessScope = Readonly<{
  userId: string;
  workspaceId: string;
  workspaceRole: "owner" | "admin" | "member";
  allowedAccountIds: readonly string[];
  activeAccountId: string | null;
}>;
```

Client-supplied user, workspace, or account IDs never grant access. Repository operations receive `WorkspaceAccessScope` or a server-derived, narrowed `AccountScope`. Every account-scoped statement binds both `workspace_id` and `account_id`. Account creation and every source-identity mutation require an active `owner` or `admin` `WorkspaceAccessScope` for the same `workspace_id`; a member or a scope from another workspace is denied.

### SQLite settings

Every writable connection uses and verifies:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
```

`foreign_keys` and `busy_timeout` are set on every connection. Initialization establishes WAL and `synchronous=NORMAL`; ordinary runtime opens only an existing managed database, verifies WAL and the exact completed registry, and never creates or migrates a file. Migrations use `BEGIN IMMEDIATE` so another writer produces a bounded busy failure rather than an interleaved schema change. Connections are always closed in `finally`.

Read-only verification uses an immutable copied/backup target when sidecar-free evidence is required, because opening a WAL database can create empty WAL/SHM sidecars even without content mutation.

### Runtime and initializer modes

Ordinary runtime and explicit initialization are separate entry points:

| Target state | Ordinary runtime | Explicit initializer |
| --- | --- | --- |
| Path absent | Fail `TRADERLINK_PLATFORM_DATABASE_MISSING`; create nothing | May create the validated parent and target, then initialize |
| Zero-byte file or SQLite file with no user tables | Fail `TRADERLINK_PLATFORM_DATABASE_EMPTY`; bootstrap nothing | May bootstrap only after proving there are no user tables |
| Application table exists but registry is absent | Fail `TRADERLINK_PLATFORM_UNMANAGED_SCHEMA` | Same failure; never adopt or overwrite |
| Registry contains unknown, changed, duplicate, or out-of-order history | Fail with the specific migration-integrity error | Same failure; never repair history automatically |
| Registry is an exact leading prefix of the manifest | Fail `TRADERLINK_PLATFORM_MIGRATIONS_PENDING`; perform no migration | Before resuming, compare the actual schema digest with the latest applied row's `post_schema_sha256`; mismatch fails `TRADERLINK_PLATFORM_SCHEMA_MISMATCH`, otherwise resume at the next order |
| Registry exactly matches the complete manifest | Compare the actual schema digest with the final row's `post_schema_sha256`; mismatch fails `TRADERLINK_PLATFORM_SCHEMA_MISMATCH`, otherwise open after foreign-key and quick-check validation | Perform the same final digest comparison and checks; succeed idempotently without adding rows |

If initialization fails before migration 1 commits, its transaction removes the registry and all migration-1 objects; an empty initializer-created SQLite file and empty WAL/SHM sidecars may remain. Retrying the explicit initializer may reuse that empty target after re-proving it has no user tables. Ordinary startup still rejects it.

If migration 1 or any later migration already committed before a later failure, those committed objects and registry rows remain. The failed migration contributes no objects or registry row. Retrying the explicit initializer requires the applied rows to be the exact untampered leading manifest prefix and the actual schema digest to equal the latest applied row's `post_schema_sha256`; it then resumes at the first unapplied order. A mismatch fails `TRADERLINK_PLATFORM_SCHEMA_MISMATCH` and is never automatically repaired or adopted. Unknown application tables always fail the separate `TRADERLINK_PLATFORM_UNMANAGED_SCHEMA` safeguard, including on a partially applied target.

## 9. Backup, recovery, and rollback

Phase 2's initial migrations are additive and target a new empty database. Any later migration that drops, rebuilds, rewrites, or reinterprets persisted data is destructive and requires a separate owner-approved checkpoint.

Before a destructive replacement migration:

1. place the application in a documented no-write maintenance state;
2. create an SQLite online backup under `C:\Users\jerac\Documents\TraderLink\private-data\traderlink-platform\backups\pre-<migration-id>-<UTC timestamp>\development.sqlite`;
3. require the source's actual deterministic schema digest to equal the latest registry row's `post_schema_sha256`, then record source and backup paths, UTC timestamps, SQLite version, registry rows/content checksums/post-schema digests, latest expected and actual schema SHA-256, every table count, WAL state, page size/count, `foreign_key_check`, `quick_check`, and file SHA-256;
4. restore that completed backup into a new target under `C:\Users\jerac\Documents\TraderLink\private-data\traderlink-platform\restore-verification\pre-<migration-id>-<UTC timestamp>\development.sqlite`;
5. require the restored target's registry to match, its actual deterministic schema digest to equal its final row's `post_schema_sha256` and the recorded source digest, all table counts and page geometry to match, the file hash to match where the online-backup result is byte-identical, `foreign_key_check` to return no rows, and `quick_check=ok`; and
6. inventory every non-superseded `hmac_key_version` and `source_account_canonicalization_version`, verify that the separately protected secrets and adapter implementations needed by those versions can be restored, without writing either secret or raw source identifier into the database evidence; and
7. begin the migration only after the database restore, secret-recovery check, and destructive plan are accepted.

`platform-database-backup.ts` implements steps 2 through 6 as an evidence helper. It inventories only version labels and calls a server-only recovery-authority verifier supplied by the later migration orchestrator; the callback confirms that the separately protected secrets and canonicalizer implementations for exactly those labels are recoverable without returning either secrets or raw source identifiers. The helper does not place the application in maintenance mode, authorize a destructive plan, switch an environment path, or start a migration. Those step-1 and step-7 responsibilities remain with the later explicitly accepted destructive-migration orchestrator/checkpoint.

Migrations are forward-only; no automatic `down` SQL is executed. A failed migration rolls back its current transaction and can be retried after code correction. If an accepted destructive migration must be reversed, stop replacement writers, preserve the failed database as evidence, restore the verified pre-migration backup to a new path, restore the exact separately protected HMAC key versions required by that database, point `TRADERLINK_PLATFORM_DB_PATH` to that restored file through an explicit environment change, and run the application commit compatible with that registry state. Never restore over or write to the legacy source.

`PRAGMA schema_version` may be recorded only as optional SQLite diagnostic context. It never establishes migration state, proves schema equivalence, replaces `post_schema_sha256`, or authorizes restore or recovery.
